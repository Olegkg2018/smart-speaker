# CLAUDE.md

Домашняя умная колонка: ESP32-S3 как тонкий клиент, вся логика на плате
S905X3 (Armbian) в Docker. Разговор ведёт облачная модель, активационное
слово ищется локально.

Подробности архитектуры, распиновки и протокола — в `README.md`.
Здесь только то, что нужно знать, прежде чем что-то менять.

## Железо и адреса

| Что | Где |
|---|---|
| Сервер | S905X3, адрес в `$HAPPY_HOST`, наружу `:8090` (внутри контейнера 8080) |
| Колонка | ESP32-S3 N16R8, адрес выдаёт роутер, подключена по USB к серверу |
| Serial колонки | `/dev/ttyACM0` **на плате**, не на машине разработки |
| Wi-Fi | задаётся в `firmware/sdkconfig` (файл в `.gitignore`) |

## Как выкатывать

Сборка образа идёт на самой плате: код туда переносится, а не собирается
локально. Адрес платы держим в переменной, чтобы он не расходился по
командам и не попадал в репозиторий:

```bash
export HAPPY_HOST=<адрес платы в домашней сети>
```

На плате код лежит по симлинку `/opt/docker/happy` — как и все остальные
контейнеры на этой машине, но физически на HDD (`/mnt/data/happy`), а не на
microSD: `data/` пишется часто (память разговоров, будильники, индекс
фонотеки каждую ночь), а у карты ограниченный ресурс перезаписи. Симлинк
прозрачен для всех команд ниже — писать можно как обычно.

```bash
# сервер
cd /home/oleg/happy
tar -czf - server/app/… | ssh "$HAPPY_HOST" 'tar -xzf - -C /opt/docker/happy'
ssh "$HAPPY_HOST" 'docker compose -f /opt/docker/happy/server/docker-compose.yml build'
ssh "$HAPPY_HOST" 'docker compose -f /opt/docker/happy/server/docker-compose.yml up -d --force-recreate'
```

Сборка занимает минуты и иногда падает по сети (таймаут pypi, IPv6 до
Docker Hub при живом IPv4) — это не ошибка кода, помогает повтор.

```bash
# прошивка: собирается на машине разработки, шьётся с платы
source /home/oleg/esp/idf_env.sh && cd firmware && idf.py build
cd build && tar -czf - happy_speaker.bin bootloader/bootloader.bin partition_table/partition-table.bin \
  | ssh "$HAPPY_HOST" 'tar -xzf - -C /home/oleg/fw'
ssh "$HAPPY_HOST" 'cd /home/oleg/fw && python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 \
  --baud 460800 --before default-reset --after hard-reset write-flash \
  --flash-mode dio --flash-freq 80m --flash-size 16MB \
  0x0 bootloader/bootloader.bin 0x8000 partition_table/partition-table.bin 0x10000 happy_speaker.bin'
```

Если менялась Kconfig-опция активационного слова (`CONFIG_SR_WN_WN9_*_TTS`) —
переносится и шьётся ещё и `build/srmodels/srmodels.bin` на `0x410000`
(смещение — в `build/flasher_args.json`). Веса самой нейросети WakeNet
живут в отдельной партиции `model`, а не в теле прошивки — три обычных
файла (`bootloader`/`partition-table`/`happy_speaker.bin`) её не трогают
вовсе, и колонка молча продолжает слушать старое слово. Разница в логе
загрузки: `AFE_CONFIG: Set WakeNet Model: wn9_computer_tts` вместо
ожидаемого `wn9_jarvis_tts` — искать через
`firmware/tools`-скрипт чтения serial (см. «Диагностика» ниже).

`idf.py monitor` требует настоящий терминал и в неинтерактивной сессии не
работает — логи колонки читаются скриптом на плате через pyserial с
дёрганьем RTS для сброса.

## Диагностика

```bash
curl -s localhost:8090/stats   # нагрузка, задержка цикла событий, активное слово
docker logs happy-speaker --tail 30
```

Ориентиры: `load_per_core` до ~0.7 и `event_loop_delay_ms` до 5 мс — звук
будет ровным. Во время речи сервер сам пишет в лог `звук ровный: N кадров`
либо `звук идёт рывками: …` — это честнее любых догадок про нехватку железа.
Стоимость каждой реплики тоже в логе (`app.pricing`).

Лог пишется не только в `docker logs` (тот живёт с текущим контейнером и
стирается на каждый `--force-recreate` — а во время активной доработки
мы это делаем часто), но и в файл на диске, который переживает
пересоздание — тот же приём, что уже спасает память разговоров:
```bash
ssh "$HAPPY_HOST" 'tail -f /opt/docker/happy/server/data/logs/happy.log'
```
Если разбор идёт уже ПОСЛЕ пересоздания контейнера — `docker logs`
бесполезен, историю искать только тут. Уровень — `LOG_LEVEL` в `.env`
(`DEBUG` на время активного тестирования, вернуть на `INFO`, когда
закончили — иначе лог быстро распухает).

## Что легко сломать

**Цикл событий.** Всё тяжёлое считается в отдельном потоке. Vosk в основном
цикле рвал WebSocket с колонкой (пинги не успевали), пересчёт частоты звука
от OpenAI давал опоздания кадров до 443 мс и рваную речь. Правило: numpy и
Vosk — только через `asyncio.to_thread`, кроме совсем мелких кусков вроде
кадра микрофона в 20 мс, где переключение потока дороже расчёта.

**Vosk не терпит общего состояния.** Модель одна на сервер (88 МБ),
распознаватель — свой у каждой сессии. Общий ломался в момент
переподключения колонки (`Failed to process waveform`), когда старая сессия
ещё жива, а новая уже пишет. Он ещё и глохнет со временем, поэтому
освежается сам после минуты тишины.

**Колонка не любит просветов в потоке.** Опустевший буфер вывода она
считала концом реплики и вставала на прогрев — отсюда «прерывистый
разговор». Сервер во время речи шлёт кадры непрерывно, прошивка ждёт
продолжения 400 мс.

**Порог громкости — адаптивный.** Фиксированный означал, что слышно только
вплотную к микрофону. Порог считается от фонового шума комнаты,
`VAD_THRESHOLD` — только нижняя граница.

**Чувствительность микрофона — тоже адаптивная, но на плате, не на сервере.**
Активационное слово приходилось почти кричать: единственное усиление до
WakeNet было статичным (`MIC_SHIFT` в `firmware/main/audio_in.c`) — удобным
одновременно и для громкого голоса вплотную, и для тихого издалека оно быть
не может. `agc_init` во фронтенде (`audio_frontend.c`) не помогает самой
активации: он стоит ПОСЛЕ WakeNet в конвейере esp-sr (`AEC -> WakeNet ->
AGC`, видно в логе загрузки). Добавлен отдельный WebRTC AGC из той же
библиотеки (`esp_agc.h`), включённый прямо в `mic_task`, до фронтенда —
активация и распознавание команды после неё получают уже выровненный
сигнал. Заодно объясняло и путаницу в распознавании: тот же случай
(«погода» услышалось как «сделай тише») — слабый сигнал, хуже отношение
сигнал/шум что для WakeNet, что для Realtime.

**Первый кадр решает.** `play_music` ждёт реальный звук, прежде чем сказать
«Играет»: YouTube умеет отдать ссылку и не отдать поток. Локальному файлу
хватает 4 секунд, сетевому нужно 25 — `yt-dlp` раскачивается небыстро.

**Музыка не должна тормозить кадр.** Микшер ждал ffmpeg прямо внутри
тактового кадра (`readexactly` на пути звука), и раскачка ffmpeg на старте
трека давала 87 опоздавших кадров из 224, худшее опоздание 259 мс. Теперь
чтение идёт отдельной задачей с буфером на секунду; нет данных — отдаём
тишину, но кадр не задерживаем. Просвет в музыке не слышен, опоздание
кадра слышно сразу.

**Порядок реплик в памяти не гарантирован событиями.** Realtime отвечает
прямо на звук, а расшифровку вопроса Whisper досылает параллельно и часто
позже ответа. Писать по факту прихода нельзя: в памяти оказывалось «ответ,
потом вопрос», и в следующем разговоре модель читала диалог со сдвигом и
отвечала не на то, что спросили. Обмен собирается парой в `_flush_exchange`.

**Сводка памяти — поля, а не проза.** Свободным текстом туда затесалось
«необходимо запускать музыку, когда она вернётся»; модель прочла это как
поручение и на вопрос о погоде включила ABBA. Поля (`человек`,
`предпочтения`, `договорённости`, `быт`) плюс пометка «справка, не
поручение» в инструкциях.

Поля не спасают от другой беды: криво распознанная реплика (Whisper
разобрал невнятную речь как польскую фразу) заставила `gpt-4o-mini` при
сворачивании придумать конкретный факт вместо того, чтобы пропустить
непонятное — в `человек` попало «Ольга Билан, российский дизайнер
одежды» (реальное публичное имя, не имеющее отношения к разговору), и
колонка на каждый следующий вопрос отвечала «Привет, Ольга!» вместо
ответа по существу. Промпт уже просил «не выдумывай» и «криво
распознано — пропусти», но этого не хватило: маленькая модель всё равно
подставила правдоподобное имя вместо пустого поля. Усилено прямым
запретом — не заполнять `человек` по ассоциации или похожести звучания,
не подставлять имя реального известного человека вместо непонятного, и
явно называть бессмысленную/иноязычную реплику тем, чем она является
(ошибкой распознавания, а не фактом). Не гарантия — маленькие модели
галлюцинируют вопреки прямым инструкциям, — но явный, специфичный запрет
надёжнее общего «не выдумывай». Если повторится — единственное быстрое
лечение симптома: `DELETE /api/memory/<устройство>` (или кнопка «забыть
всё» на странице `/`), спорную сводку саму по себе не почистить.

Корень именно этого случая нашёлся отдельно: конфиг транскрипции Realtime
API (`transcription` в `session.update`, `realtime.py`) не указывал
`language` вовсе — Whisper сам угадывал язык по звуку и на нечётком
сигнале несколько раз подряд ошибался вслепую (польский, немецкий,
деванагари вместо русской речи). Эта транскрипция не влияет на то, как
сама модель понимает команды (та слушает аудио напрямую) — только на то,
что попадает в историю и сводку, но именно оттуда чужеязычный мусор и
просачивался в проблемы вроде «Ольги Билан». Добавлено явное
`language: settings.whisper_language`.

**Голосовая модель иногда не вызывает инструмент вопреки прямой
инструкции.** На «какая погода на завтра» `gpt-realtime` один раз просто
ответила из своих знаний («сейчас +25 и ясно» — неверно и не про
завтра), не позвав `get_weather` вовсе — в логе не было ни строки
`инструмент get_weather(...)`. Промпт уже прямо запрещал отвечать по
памяти на вопросы о погоде/новостях; усилен конкретным примером
(`period` должен соответствовать вопросу — «завтра» это `tomorrow`, не
`now`). Это не гарантия: надёжность вызова функций у голосовых моделей
ограничена самой природой модели (см. ниже про `-2.1-mini`, которая
путает инструменты ещё чаще) — конкретные, специфичные формулировки в
промпте снижают частоту, но не исключают полностью.

**DNS на плате отваливается.** Цепочка `docker → systemd-resolved`
периодически подвисает: первый запрос к облаку падал с
`NameResolutionError`, отвечал только повтор — 4-7 секунд на реплику. В
`docker-compose.yml` обоих проектов прописаны свои DNS (1.1.1.1, 8.8.8.8).

**Полуоткрытое соединение держит комнату мёртвым устройством.** Колонка
теряет питание без штатного закрытия сокета (роутер/NAT промолчал, ни FIN,
ни RST) — без пинга такое соединение висит в `PeerSet` часами (стандартный
TCP keepalive в Linux — 2 часа), а переподключение того же устройства
садится вторым в ту же комнату вместо замены старого; сервер может слушать
мёртвый микрофон вместо живого. Двойная защита: `ws_ping_interval=15.0,
ws_ping_timeout=15.0` в `uvicorn.run` закрывает мёртвый сокет сам за 30
секунд, а `PeerSet.add()` (`app/peers.py`) вдобавок сразу вытесняет любого
существующего пира с тем же `device`+`role`, не дожидаясь пинга.

**Зависшая прошивка не спасалась собственным сторожем.** Колонка перестала
отвечать после какого-то события (не воспроизведено намеренно, застали
постфактум) — серийный порт молчал вообще, ни единой строчки лога больше
90+ минут. Прикладной сторож в `main.c` (`watchdog_task`, проверяет
`happy_ws_connected()` раз в 5 секунд и должен сам перезагружать плату
через `esp_restart()` после 90 секунд простоя) не сработал: он сам —
такая же FreeRTOS-задача, и если зависла вся система целиком (а не только
сетевой клиент), то зависла и она. Разбудить такую плату может только
внешнее вмешательство — в этот раз ручной RTS-сброс через serial
(`ser.setRTS(True/False)`), после чего колонка загрузилась чисто и сама
переподключилась.

Настоящую причину зависания найти не удалось (лог обрывается без единой
подсказки) — но нашлась защита последнего рубежа, которая ДОЛЖНА была уже
стоять и не стояла: Task Watchdog Timer (аппаратный, не прикладной)
технически был включён и мониторил обе idle-задачи
(`CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0/1=y`, таймаут 5 секунд), но при
срабатывании только писал ошибку в лог, а не паниковал и не
перезагружал (`CONFIG_ESP_TASK_WDT_PANIC` не был включён). Если зависание
блокирует и сам вывод в serial, такое предупреждение всё равно не
спасает — TWDT это единственный механизм, который может прервать
безнадёжно зависшую систему без физического вмешательства. Включили
`CONFIG_ESP_TASK_WDT_PANIC=y` (и легаси-алиас `CONFIG_TASK_WDT_PANIC=y`) в
`firmware/sdkconfig` — вместе с уже настроенным
`CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y` (`REBOOT_DELAY_SECONDS=0`) это
должно приводить к немедленной перезагрузке чипа, если TWDT когда-нибудь
поймает зависшую idle-задачу снова. Не проверено на настоящем повторении
зависания (оно не воспроизводится по требованию) — это защита на
будущее, а не подтверждённое лечение конкретной причины. `sdkconfig` не в
git — эта настройка видна только здесь и в самом файле на диске.

**Смена wake-word модели молча не срабатывает без перепрошивки `model`.**
В тот же день, что и переключение слова на «Джарвис» (Kconfig-опция
`CONFIG_SR_WN_WN9_*_TTS`), колонка перестала реагировать на голос — сама
жалоба выглядела точь-в-точь как повтор предыдущего дневного инцидента
(«не работает после перезагрузки»), но причина оказалась совсем другой и
куда прозаичнее: веса нейросети WakeNet лежат не в теле прошивки, а в
отдельной flash-партиции `model` (`build/srmodels/srmodels.bin`,
смещение `0x410000`, см. `build/flasher_args.json`). Обычный флоу
обновления прошивки трогает только `bootloader`+`partition-table`+
`happy_speaker.bin` — этого достаточно для любых изменений кода, но не
для смены самой модели активационного слова: приложение при старте
берёт первую подходящую по префиксу модель ИЗ ПАРТИЦИИ (`esp_srmodel_
filter`), а не то, что скомпилировано в текущий бинарник, поэтому после
обычной прошивки колонка продолжала слушать старое слово «компьютер» —
тихо, без единой ошибки в логе, только фраза в логе загрузки
`AFE_CONFIG: Set WakeNet Model: wn9_computer_tts` вместо ожидаемого
`wn9_jarvis_tts` выдавала правду. Ушёл час на разбор двух серверных
логов и serial-консоли, прежде чем стало ясно, что зависания не было
вовсе — просто активационное слово молчаливо осталось прежним, и
пользователь, говоря «Джарвис», не мог получить ответа. Урок задним
числом: при любой смене `CONFIG_SR_WN_*` (и вообще любой Kconfig-опции,
влияющей на состав `srmodels.bin`) обязательна отдельная команда
прошивки партиции `model` — это НЕ покрывается стандартным рецептом
выше, и последствия пропуска выглядят как полная тишина в ответ на
голос, а не как явная ошибка.

**Состояние может зависнуть, если бэкенд не позвал колбэк до конца.**
`LISTENING`/`THINKING`/`SPEAKING` — промежуточные, кто-то обязан вывести
из них обратно в `IDLE`. Ловили дважды разными путями: Realtime не прислал
`response.done` (зависла в `THINKING`), и реплика закончилась ровно в
момент планового часового переподключения (`_proactive_refresh` на
секунду обнуляет `self._conn`) — `end_utterance()` при пустом `_conn`
раньше молча ничего не делал, и колонка простояла «слушаю» несколько
часов до ручного вмешательства. Правка по месту (`end_utterance` теперь
зовёт `turn_done()` и раньше отвечает «секунду, переподключаюсь») плюс
общий сторож — `Session._watch_state`, `_STATE_WATCHDOG_S = 45` в
`session.py`: если состояние не сменилось за 45 секунд, сессия сама
возвращается в `IDLE` и логирует предупреждение. Второй случай не
исключает третьего с другой причиной — сторож на этот случай и добавлен.

Третий случай пришёл в тот же день с обратной стороны: правка выше
превратила молчаливое зависание в озвученное — колонка честно призналась
«секунду, переподключаюсь», но само подключение оказалось не пустой
формальностью. `self._client.realtime.connect().__aenter__()` не имел
таймаута вовсе — сетевая заминка подвесила его на 14+ минут без единого
исключения, и `_proactive_refresh` после первой неудачи просто ждал
«штатного разрыва», которого больше не будет: рвать уже нечего, старое
соединение уже закрыто само. Каждая следующая попытка реплики повторяла
одно и то же и озвучивала это заново — колонка зациклилась на фразе.
Три правки разом: `_CONNECT_TIMEOUT_S = 15` оборачивает `connect()` в
`asyncio.wait_for` (зависание — это быстрая ошибка, а не вечное ожидание);
`_reconnect_with_retry()` пробует до трёх раз с растущей паузой (3/10/30 с)
вместо одной попытки — им пользуются и плановое, и реактивное
переподключение; `_RECONNECT_ANNOUNCE_MIN_GAP_S = 30` не даёт озвучивать
«секунду, переподключаюсь» чаще раза в этот срок, даже если реплики
продолжают приходить одна за другой, пока связи всё ещё нет.

Четвёртый случай — в тот же день, третий раз подряд с обратной стороны:
таймаут на новое соединение стоял, а на закрытие СТАРОГО (`old_task` и
`old_manager.__aexit__()` в `_proactive_refresh`) — нет, и колонка снова
зависла на минуты ровно там же по сути, просто чуть дальше по коду.
Первая попытка починить — обернуть оба ожидания в `asyncio.wait_for(...,
timeout=...)`, как и для нового соединения, — **не сработала и это стоит
запомнить отдельно**: если ждущая задача сама глотает `CancelledError`
(или сетевой вызов внутри неё не откликается на отмену), `wait_for` всё
равно ждёт её настоящего завершения — таймаут только откладывает
исключение, а не гарантирует возврат. Проверено воспроизведением: тест с
такой обёрткой зависал в точности как продакшен. Единственный рабочий
выход — не ждать синхронно вовсе: `old_task.cancel()` плюс
`asyncio.create_task(_drain_cancelled(...))` в фоне, и сразу переходить к
новому соединению, не дожидаясь, чем закончится закрытие старого.

Пятый случай — тем же вечером, и это оказалось самое важное место: тот же
непомогающий `wait_for` стоял и вокруг САМОГО открытия нового соединения
(`_CONNECT_TIMEOUT_S` в `start()`) — колонка зависла на 11+ часов молча,
`попытка 1/3 поднять Realtime — начинаю` осталась последней строчкой в
логе. Раз `wait_for` в принципе не гарантирует возврат, обёртка вокруг
open() ничем не отличается от обёртки вокруг close() — чинить нужно было
там же и так же. Решение сложнее, чем для close(): просто «бросить и
забыть» нельзя — открытие соединения даёт результат, который жалко терять,
и который нельзя присвоить `self._conn` из фонового потока не глядя, а то
он перезапишет уже поднятое кем-то другим (второй попыткой ретрая)
соединение. Ввели `self._connect_generation` (растёт на каждый `start()`):
если попытка не уложилась в таймаут, `start()` бросает `TimeoutError`
сразу (вызывающий код — `_reconnect_with_retry` — пробует снова), а
опоздавшая попытка, если всё же завершится, либо приживается через
`_adopt_late_connect` (если с тех пор никто не подключился и это всё ещё
последняя попытка), либо тихо закрывается (если кто-то успел раньше).
Проверено тестами на оба случая: `test_late_connect_is_adopted_if_still_
the_current_attempt`, `test_late_connect_is_discarded_if_something_else_
already_connected`.

Шестой случай — и это была настоящая причина всех пяти предыдущих: не
сетевая заминка, а самоотмена. `self._refresh_task` — это и есть задача,
исполняющая `_proactive_refresh()`. Когда час истекает, она сама вызывает
`start()`, а первая строчка `start()` звала `self._refresh_task.cancel()` —
то есть отменяла саму себя. `cancel()` на текущей задаче не убивает
мгновенно: `CancelledError` влетает на ближайшей же точке `await` (тут же,
внутри `start()`) и тихо гасит всю цепочку задач — не пойман веткой
`except Exception` (`CancelledError` с 3.8 — не `Exception`), в логе ни
строки, `self._conn` остаётся `None` навсегда, никто больше не пробует
переподключиться. Ровно так и выглядело: активацию слышит, а голос
собеседника — нет, и «секунду, переподключаюсь» на каждой попытке. Все
таймауты на connect/close из случаев 3–5 были не лишними (это реальная
защита от настоящих сетевых зависаний), но лечили не тот симптом. Фикс —
`if self._refresh_task is not None and self._refresh_task is not
asyncio.current_task(): self._refresh_task.cancel()`. Тест
(`test_proactive_refresh_does_not_cancel_itself`) воспроизводит один в
один: настоящий `_proactive_refresh`, запущенный как настоящая
`self._refresh_task`, с настоящим `start()` — без фикса падает с той же
`CancelledError` из `asyncio.wait()` внутри `start()`, что и в проде.

Седьмой случай — и он про то, что оба предыдущих способа «сдаться» были
двумя разными местами с одним и тем же изъяном: **отказ был окончательным**.
Жалоба всегда одна и та же — колонка (и сателлиты, сессия общая) в
состоянии «Готова», а на реплику отвечает «Голосовой сервис недоступен»
или «пока недоступен». Настоящая пара доказательств из логов (по
`docker logs --timestamps`, время в тексте — местное): после перезагрузки
платы колонка подключалась в 22:19:36, а в 22:20:07 `_start_voice` падал
(сеть/DNS ещё не поднялись, Realtime не отвечал 15 с) — и сессия
оставалась `_voice_failed = True` до 19:41 следующего дня, ~21 час, пока
колонку кто-то не переподключил и сессия не пересоздалась. Первый запуск
не повторялся вообще, в отличие от переподключения уже работающего
Realtime. Второй такой же изъян нашёлся рядом, ещё не сработавший вживую:
`RealtimeVoice._reconnect`/`_proactive_refresh` после трёх неудачных
попыток (`_RECONNECT_ATTEMPTS`, ~43 с суммарно) озвучивали «пока
недоступен» и сдавались навсегда — `_conn` оставался `None`, а плановое
обновление при `_conn is None` молча выходит. Любая сетевая пауза дольше
минуты (роутер, провайдер, перезагрузка платы) убивала бы голос так же.
Правки: `Session._start_voice` теперь повторяет запуск в цикле с паузами
`_VOICE_RETRY_DELAYS_S` (5/15/30/60 с и дальше раз в 60 с), об отказе
говорит один раз, снимает `_voice_failed` при успехе, отменяется в
`_shutdown`; `RealtimeVoice._revive_loop` продолжает попытки раз в
`_REVIVE_INTERVAL_S = 60` после исчерпания трёх, пока не получится или
`close()` не выставит `_closed`. Отдельно, чтобы не путать: сама фраза
озвучивается не через Realtime, а отдельным запросом синтеза речи
(`_announce` → `tts-1`), поэтому колонка легко говорит «нет подключения»
при мёртвом голосовом WebSocket. Не исключён и настоящий зависший
контроллер (в тот же день на serial была тишина, а сервер держал
«призрачное» соединение колонки) — это другая, пока не найденная причина,
и её лечит только защита последнего рубежа из «Зависшая прошивка…» выше.

**Сетевой вызов из mic_task снова сажал чувствительность и рвал речь.**
Тот же урок, что раньше уже был усвоен на Opus-кодеке («первая версия звала
кодек синхронно из afe_fetch... валила их тайминги»), пришлось выучить
второй раз на своей же более новой фиче. `mic_level` (для окна продолжения
разговора) считался в `mic_task` — самой приоритетной аудио-задаче (6) —
и тут же, в этой же задаче, отправлялся по WebSocket колбэком
`on_raw_level` → `happy_ws_send_json` → `esp_websocket_client_send_text`
с таймаутом 200 мс. Жалоба пользователя: активационное слово и обычная
речь стали требовать говорить вплотную к микрофону, хотя раньше слово
ловилось и с трёх метров, плюс речь временами шла рывками — то есть
регрессия ровно там, где раньше уже чинили AGC/MIC_SHIFT, хотя те
настройки не менялись. Настоящая причина не в громкости: блокирующая
сетевая отправка раз в ~100 мс периодически задерживала `mic_task`,
DMA-буфер микрофона (всего 4 дескриптора — секунды на буферизацию нет)
переполнялся, кадры терялись или приходили с разрывом — WakeNet и
Realtime получали худшее отношение сигнал/шум и обрывки фразы, что и
ощущалось как «надо говорить громче/ближе» и как рывки в самой речи.
Чинится тем же способом, каким уже чинили Opus: `mic_task` кладёт
значение в очередь FreeRTOS длины 1 через `xQueueOverwrite` (никогда не
блокируется, старое значение просто заменяется), а сама отправка ушла в
отдельную задачу `level_report_task` низкого приоритета (3, ниже
mic_task/afe_fetch/opus_codec, выше watchdog). Урок для будущего: **любой
новый колбэк, вызываемый прямо из `mic_task`, нужно сразу проверять на
блокирующие вызовы** — это самая приоритетная задача в системе, и то, что
"это же просто маленький JSON", ничего не значит, если под ним лежит
сетевой вызов с таймаутом.

**Реконнект в ту же комнату мог сесть в ещё не убранную старую сессию.**
Колонку обесточили во время играющей музыки — после включения она
подключилась к серверу (лог это подтверждал), но светодиод горел
«тусклым сиреневым» («играет музыка», см. `led.c`) и на экране не
появлялось «Готова», хотя играть было уже нечему: старая сессия
разорвалась вместе с питанием. Причина — гонка в `app/main.py::stream()`:
одна сессия на комнату держится в `_rooms`, создаётся, только если
`_rooms.get(room) is None`, а убирается в `finally` ПОСЛЕ того, как
`session.serve()` вернётся. Пир снимается с сессии синхронно (в её же
`serve()`/`finally`), а вот `_close()`/`_shutdown()` следом — асинхронные
и небыстрые (гасят голосовой бэкенд, микшер, сторожей). Если колонка успела
переподключиться в этот промежуток, `_rooms.get(room)` ещё возвращал
старую (уже пустую, но не удалённую) сессию — новый пир садился в НЕЁ,
наследуя её состояние (`self._state == PLAYING` от прерванной музыки)
вместо свежей `IDLE`. Фикс — одна строка: пересоздавать сессию не только
когда её нет вовсе, а когда она `is_empty` (`if session is None or
session.is_empty`) — не важно, успел ли её `_close()` уже отработать.
Тест воспроизводит гонку явно (`test_finally_does_not_delete_a_session_
that_was_replaced`): старая сессия дотирает `finally` уже ПОСЛЕ того, как
реконнект создал новую — не должна вытеснить её из `_rooms`.

Фикс оказался НЕ полным — тот же симптом (фиолетовый светодиод, нет
«Готова») повторился на следующей же перезагрузке. Причина в том, что
`is_empty` в момент реконнекта часто ещё **не true**: колонка теряет
питание без штатного закрытия сокета (см. «Полуоткрытое соединение» выше),
и её старый `Peer` какое-то время всё ещё числится в `PeerSet` как
«живой» — `session.is_empty` возвращает `False`, реконнект вытесняет
призрака по совпадению `device`+`role` (`PeerSet.add`), но САМА сессия
(со всем её состоянием — `_state`, открытое окно продолжения, голосовое
соединение) переиспользуется как ни в чём не бывало. Мой фикс закрывал
только редкую щель (сессия уже пуста, но ещё не удалена из `_rooms`), а
не основной путь (сессия не пуста — в ней призрак). Настоящая починка
(сброс состояния при вытеснении призрака речевого устройства, а не
только при `is_empty`) — ещё не сделана; пока лечится только полным
перезапуском контейнера сервера (`docker compose ... up -d
--force-recreate`), который убивает все сессии в памяти разом —
перезагрузка одной колонки это НЕ делает, зомби живёт на сервере, а не
на плате.

**Продолжение разговора зациклилось само на себе — принудительный вызов
инструмента плюс несовершенное эхоподавление.** Ночью колонка сама
заговорила без активации, несколько часов подряд гоняя музыку и
озвучивая странности вроде «Спасибо за субтитры Алексею Дубровскому!» и
«музыка пока не прекратилась, попробую снова остановить» — то есть
буквально читала вслух то, что сама играла, принимая своё же эхо за
чужую речь. Это НЕ побочный эффект зомби-сессии выше — то же самое
воспроизвелось и в совершенно свежей, нормально подключённой сессии, без
единой перезагрузки. Механизм: эхоподавление на плате не до конца
вычитает громкую музыку (уже известное ограничение, см. «Известные
ограничения» в README), обрывок этого эха проходит грубую проверку по
громкости (`SpeakerLevel`, сравнение по амплитуде, не голос) — и тут же
срабатывает `tool_choice="required"` на реплике-продолжении (см.
«Realtime-модель нельзя сменить внутри сессии» выше): модель ОБЯЗАНА
вызвать какой-то инструмент, даже если реально ничего не сказано, и
вместо молчания вызывает что-то правдоподобное из контекста (снова
`play_music` с тем же треком) — что рождает новый звук, который снова
просачивается в микрофон, и цикл повторяется сам собой. `_finish_turn`
и так не открывает окно продолжения, пока играет музыка (`not
self._mixer.is_playing`), но этого недостаточно: реплика, что музыку
ОСТАНАВЛИВАЕТ, сама может открыть окно (музыка к этому моменту уже не
играет), а дальше цикл заводится с нуля тем же эхо-обрывком. Пока
`FOLLOWUP_ENABLED=false` (выключено в `.env` на плате после инцидента) —
принудительный вызов инструмента без реального содержания слишком
опасен рядом с любым источником звука от самой колонки. Прежде чем
включать обратно, нужно: либо не форсировать `tool_choice` вовсе (пусть
модель имеет право промолчать, если ничего не расслышала), либо резко
ужесточить гейт по громкости специально на время играющей музыки, либо
и то и другое.

Разбирая ещё один такой случай — уже БЕЗ играющей музыки, колонка молчала
в состоянии ожидания и вдруг сама заговорила, — упёрлись в то, что
**переход между `IDLE`/`LISTENING`/`THINKING`/`SPEAKING` нигде не
писался в текстовый лог**, только уходил устройству по WS. Проверить
постфактум, что показывал светодиод и сколько реально длилось окно
продолжения (3 с, `FOLLOWUP_WINDOW_S` — не 4, это была моя ошибка,
спутал дефолт в `config.py` с тем, что реально стояло в `.env` на плате),
было нечем: ни лога, ни (после нескольких `--force-recreate` за время
разбора) даже истории контейнера. Добавили `log.info("состояние: %s → %s",
...)` в `Session._set_state` — теперь секунда и предыдущее состояние
видны напрямую в `docker logs`, а не восстанавливаются по памяти и
светодиоду. Отдельный урок про сам разбор: пересоздание контейнера
(`--force-recreate`) стирает его лог целиком — если инцидент разбирается
не сразу, снимать `docker logs` **до** любого перезапуска, иначе
доказательства пропадают вместе с контейнером.

## Внешние сервисы

**YouTube не отдаёт аудио** с серверных адресов: скачивание получает 403,
веб-клиенты требуют PO-token. Поиск при этом работает — поэтому сбой
выглядит странно, будто трек найден, но молчит. Основной источник —
SoundCloud, YouTube оставлен запасным.

**Telegram читается без API** — через веб-превью `t.me/s/<канал>`, только
публичные каналы и только с User-Agent браузера, иначе страница приходит без
постов. Пост там не заголовок, а свободный текст с эмодзи и призывами
подписаться: всё это вычищается, иначе колонка читает вслух «подписаться
стрелка вправо».

**Realtime переотправляет весь контекст** на каждый ответ, поэтому длинный
разговор дорожает с каждой репликой. Ограничено через `truncation`
(`REALTIME_CONTEXT_TOKENS`).

**Доступ к моделям раскатывается не мгновенно.** `gpt-realtime-2.1-mini`
несколько часов отвечала `model_not_found`, хотя уже была в списке моделей.
Если модель «не существует», а ключ рабочий — это про права, а не про код.

Грабли повторились дважды на TTS: `gpt-4o-mini-tts` числится в
`/v1/models`, но на запрос отвечает 403 «does not have access»; `tts-1-hd`
в списке нет вовсе. Рабочая — `tts-1`. Прежде чем менять модель, проверяй
не список, а живой вызов: список врёт.

**Realtime-модель нельзя сменить внутри сессии — сложное отдаём «эксперту».**
Mini дёшева, но слабо рассуждает; полная Realtime-модель ≈3.2× дороже (аудио
32/64 против 10/20 $ за 1М, `app/pricing.py`). Первая мысль — две Realtime-
модели и полная только на продолжениях — упирается в то, что `model` (как и
`voice`) задаётся лишь при подключении и `session.update` его не меняет
(документация SDK); значит, два соединения, гейтинг колбэков, синхронизация
контекста через `instructions` и риск разного голоса, и всё это поверх кода,
где уже поймано шесть зависаний. Готового переключения моделей в сессии у
OpenAI нет. Выбран паттерн Chat-Supervisor из официального
[openai/openai-realtime-agents](https://github.com/openai/openai-realtime-agents):
mini разговаривает и озвучивает, а сложное отдаёт инструменту `ask_expert`
(`app/tools/expert.py`) — второму, отдельному вызову к Responses API, ровно как
уже сделан `web_search`. Голос всегда один. На реплике-продолжении
(`begin_utterance(followup=True)`) `RealtimeVoice.end_utterance` шлёт
`response.create(response={"tool_choice": "required"})`: не имя `ask_expert`,
а именно «required» — иначе «поставь таймер» на продолжении ушло бы к
эксперту, который таймер не поставит. Оговорка: на «спасибо» после ответа
тоже уйдёт вызов (эксперт отвечает на такое одной короткой фразой). Цена —
пауза 2–4 с, пока эксперт думает, без фразы-заполнителя (в принудительном
режиме она ненадёжна); состояние `THINKING` при этом видно. Тарифа
эксперта в `pricing.py` нет, в лог пишутся время и токены. Список моделей у
ключа врёт (см. выше) — доступ к `EXPERT_MODEL` проверять живым вызовом.

## Соседний проект на той же плате

Рядом крутится `xiaozhi-esp32-server` — чужой сервер под ту же ESP32,
поднятый для сравнения. Это отдельный контейнер и отдельная прошивка,
с нашим `happy` он не связан ничем, кроме железа.

| | happy | xiaozhi |
|---|---|---|
| Исходники | этот репозиторий | `/mnt/data/xiaozhi-esp32-server` |
| Данные | `/opt/docker/happy/server/data` | `/mnt/data/xiaozhi-server` |
| Порты | 8090 | 8005 (ws), 8006 (OTA) |
| Схема | речь-в-речь (Realtime) | `ASR → LLM → TTS` |

Прошивка у платы может быть только одна: чтобы попробовать xiaozhi, её
перешивают их бинарником, обратно — нашим (`/home/oleg/fw`, смещения в
`flasher_args.json`).

Что оттуда пригодилось нам: приём с кольцевым буфером перед активационным
словом, отладчик звука по UDP, инициализация панели ST7789. Что не
пригодилось: их вывод на экран (55 КБ C++ поверх LVGL, завязан на их
`board.h`) и конвейерная схема разговора — речь-в-речь мы выбрали
сознательно.

Замер локального синтеза на этой плате (Cortex-A55, 4 ядра, без GPU):
Piper RTF 0.57, Silero v3 RTF ~0.9 после прогрева. Прогрев Silero стоит
40 секунд и делается при старте сервера, иначе первая фраза после
перезапуска ждёт всё это время. Задача почти не параллелится: учетверение
потоков даёт 9% прироста, всё упирается в одно ядро.

## Настройки, которые меняют поведение сильнее всего

Всё в `server/.env` (образец — `.env.example`), пересборка не нужна,
достаточно `up -d --force-recreate`.

- `VOICE_PROVIDER` — `openai_realtime` (спич-ту-спич) или `claude`
  (Whisper → Claude → Piper, работает без интернета к OpenAI).
- `OPENAI_REALTIME_MODEL` — `gpt-realtime`. Есть и `-2.1-mini` втрое
  дешевле, но на неоднозначной речи она чаще путает инструменты.
- `STT_PROVIDER` / `TTS_PROVIDER` — `local` или `openai`; облачные заметно
  быстрее локальных на этом железе.
- `EXPERT_MODEL` — текстовая модель для сложных вопросов (инструмент
  `ask_expert`); пусто — инструмент выключен и модели не показывается.
  `EXPERT_FORCE_ON_FOLLOWUP` (по умолчанию `true`) — на репликах-продолжениях
  вызов инструмента обязателен.

Активационное слово — это не настройка `.env`, а Kconfig-опция прошивки
(`CONFIG_SR_WN_WN9_*_TTS` в `firmware/sdkconfig`/`sdkconfig.defaults`):
ESP-SR идёт с набором готовых предобученных моделей WakeNet (сейчас
«Джарвис», было «Компьютер»), между ними можно переключаться без
переобучения — но только пересборкой и перепрошивкой платы, на лету не
меняется. Слово подлиннее надёжнее: короткие притягивают созвучия
(«Алиса» ловится на «Ларису»).

## Планы развития

Не готовые решения, а то, что обсуждали и стоит учитывать при следующем
подходе к теме.

**Продолжение разговора без повторного слова — отключено после
инцидента, см. «Что легко сломать».** Живая проверка нашла реальный
цикл ложных срабатываний (принудительный вызов инструмента на обрывке
собственного эха колонки — колонка часами сама с собой «разговаривала»
и крутила музыку без единой команды). `FOLLOWUP_ENABLED=false` в `.env`
на плате, пока не переделана защита. Описание ниже — как было
спроектировано и почему этого оказалось недостаточно.

После ответа колонка недолго (`FOLLOWUP_WINDOW_S`, по
умолчанию 4 с) слушает без нового активационного слова — если ответил не
на музыку и то же устройство уже присылало `mic_level`. Защита от
случайного шума/чужого голоса/телевизора — сравнение СЫРОГО (до AGC на
плате) уровня громкости с эталоном прошлой реплики
(`app/audio/speaker_level.py`, `FOLLOWUP_SPEAKER_MIN_RATIO`, по умолчанию
0.5): автоусиление специально стирает разницу в громкости источников, а
для этой проверки разница и нужна. Прошивка шлёт сырой уровень отдельным
`{"t":"mic_level","raw":N}` не на каждый кадр, а раз в ~100 мс — только
пока сервер слушает. Сервер включает этот протокол на устройстве через
поле `"levels"` в `ready`; старая прошивка его просто не пришлёт, и
фича молча не активируется — чистый откат к обычному вопрос-ответу.
Выключено по умолчанию (`FOLLOWUP_ENABLED=false`), включается в `.env`
без пересборки. 255 тестов (было 233) покрывают всю логику ветвления
(`_finish_turn`, гейт в `_on_binary`, резервный сторож `_watch_followup`)
изолированно — сам разговор с реальной сменой говорящего в комнате ещё
не проверялся.

**Экран 2.0" ST7789V — сделано, но живьём не проверено.** Отрисовка
переехала на плату: сервер шлёт `{"t":"text","value":"…"}`, а рисует
`display_st7789.c`. Кадр собирается полосами по 32 пикселя в PSRAM —
целиком RGB565 240x320 (150 КБ) во внутреннюю память не влезает. Шрифт с
кириллицей запечён в прошивку (`tools/make_font.py`, 168 глифов, 8 КБ).
Инициализация панели — штатный `esp_lcd`, взята из `bread-compact-wifi-lcd`
у 78/xiaozhi-esp32; их собственный вывод на C++ поверх LVGL не переносится.

Экран физически не подключён — код собирается и тесты шрифта проходят на
хосте, но на живой панели ничего не проверялось. Распиновка под гребёнку
платы XH-S3E-AI: `MOSI=41`, `CLK=42`, `CS=44 (RXD)`, `DC=43 (TXD,
перемычка)`, `RST` на 3V3 (сброс командой), подсветка внутри модуля. Пять
контактов из семи садятся в разъём как есть; `DC` и `RST` отгибаются —
`RST` обязательно, иначе он попадёт на `UIN` с пятью вольтами. UART при
этом свободен: консоль идёт по USB (`ttyACM`).

**Мимика на большом экране — не начато.** Когда экран заработает, его
надо чем-то заполнить. У 78/xiaozhi-esp32 это LVGL с коллекцией PNG на
21 эмоцию — тянуть LVGL ради этого не хочется. Дешевле: наш же
`make_font.py` умеет печь любой размер, значит можно сгенерировать второй
шрифт кегля 96 из десятка символов-лиц. Ограничение: в DejaVuSans
пиктограмм немного и цветных эмодзи нет вовсе — будут одноцветные
силуэты, зато килобайты флеша и ноль зависимостей. Альтернатива — взять
готовые Twemoji 64×64 из
[78/xiaozhi-assets-generator](https://github.com/78/xiaozhi-assets-generator)
и перегнать в RGB565.

**Распознавание голоса (кто говорит) — реально достижимо.** Раньше сказал,
что это едва ли возможно на этом железе — неверно. В `xinnan-tech/
xiaozhi-esp32-server` (сервер, который пользователь тестировал под тем же
модулем ESP32, см. `voiceprint_provider.py`) это обычный HTTP-вызов к
внешнему API `/voiceprint/identify` с порогом схожести — тот же принцип,
что у нас уже работает с погодой и распознаванием речи: облако считает,
плата и сервер только передают. Стоит вернуться к этой идее.

**Суммирование памяти — сделано.** Вытесненное из окна сворачивается
`memory_summary.fold_in` через `gpt-4o-mini` (отдельная дешёвая модель, не
та, что ведёт разговор). Сводка структурная: поля `человек`,
`предпочтения`, `договорённости`, `быт`. Прозой уже обожглись — см.
«Сводка памяти — поля, а не проза» выше.

Их подход отличается моментом: `mem_local_short` в xiaozhi сворачивает всё
одним разом при закрытии сессии, мы — на каждом вытеснении. Наш дороже по
вызовам, зато переживает внезапный обрыв; у них при падении контейнера
сессия теряется несвёрнутой.

**Выбор модели — не копировать.** Там же дежурил `deepseek-chat` —
вероятная причина, по которой колонка на этом проекте была «тупой»: слабее
Claude Opus 5 и `gpt-realtime-2.1-mini` в надёжности вызова инструментов и
общей адекватности ответов. Память и логирование там были в порядке —
дело было в модели, не в архитектуре.

**Учёт расходов в Telegram.** Кабинет OpenAI для «остатка на счету» не
подходит — данные там с задержкой и нужны отдельные права, поэтому
стоимость уже считается на месте по токенам ответа (`app/pricing.py`).
Сейчас это работает только за одну сессию и никуда не сохраняется. Чтобы
слать в Telegram «сколько потрачено» — по запросу голосом или раз в сутки
сводкой, — нужно копить этот же посчитанный итог на диск (day-to-day,
как `data/alarms` или `data/lists`), а не искать API «остатка», которого
для такого ключа попросту нет.

**Другие голосовые модели, кроме `gpt-realtime-2.1-mini`.** Стоит
свериться с актуальной документацией, а не полагаться на память — цены и
состав предложений меняются. Архитектура уже рассчитана на смену бэкенда
(`VOICE_PROVIDER=openai_realtime` или `claude`, см. `app/voice.py`), так
что третий вариант (например, Gemini Live API) — это ещё один класс рядом
с `RealtimeVoice`, а не переписывание с нуля.

**Telegram-бот в обе стороны.** Сейчас бот только пишет наружу — дублирует
разговор (`app/notify.py`) и читает публичные каналы для новостей
(`app/tools/telegram.py`); входящие сообщения сервер не читает вовсе.
Чтобы бот принимал задания колонке, составлял и выводил списки, брал текст
или файл на осмысление («прочти и расскажи, что думаешь») — нужен
long-polling или webhook и разбор команд. Это открывает текстовый канал
управления умным домом снаружи разговора на кухне (дом на 192.168.2.14
управляется через HA), и доверие к этому каналу стоит обдумывать отдельно
от голоса рядом с колонкой, а не переносить как есть.

**Тест на `agent.py` (ручной цикл tool-use у Claude) не написан.** Ревью
августа 2026 просило хотя бы один тест на связку «tool_use → tool_result →
повторный запрос» с моком Anthropic-клиента. `session.py` тестами уже
покрыт (`tests/test_session.py`), а `agent.py` — нет: код не используется
в рантайме при `VOICE_PROVIDER=openai_realtime` (сейчас так и стоит), но
именно поэтому он опаснее всего в день, когда его снова включат. Отложено
по объёму работы (мокать стриминг Anthropic сложнее, чем bare-instance
тесты на Session), не забыто.

**Opus вместо сырого PCM — сделано.** Канал сжат примерно в 15 раз.
`firmware/main/audio_opus.c` — обёртка над `espressif/esp_audio_codec`,
`hello`/`ready` согласуют кодек, откат на PCM при отсутствии Opus с любой
стороны штатный. Первая версия звала кодек синхронно из `afe_fetch` и
`websocket_task` и валила их тайминги: стека 4096 не хватало под кодек
(Guru Meditation на активационном слове), а конкуренция за приоритет 5
рвала WebSocket ровно в момент начала записи. Теперь это отдельная задача
с очередями.

**Буфер перед активационным словом — сделано.** `firmware/main/wake_cache.c`:
кольцо на секунду в PSRAM, при активации накопленное уходит первым, до
живого потока. По кнопке кольцо сбрасывается — там начало реплики известно
точно. Раньше слитное «компьютер, включи музыку» приходило как «ключи
музыку».

**Отладчик звука — сделано.** `firmware/main/audio_debug.c` дублирует то,
что слышит микрофон, по UDP; `firmware/tools/listen.py` принимает и пишет
в wav. По умолчанию выключен. Появился после того, как качество
распознавания дважды пришлось оценивать по косвенным признакам —
расшифровкам на румынском и доле опоздавших кадров.

Первое включение сразу нашло реальный баг: `happy_audio_debug_start()`
стоял в `app_main()` до `happy_wifi_start()` — `socket()` падал с
`assert failed: tcpip_send_msg_wait_sem (Invalid mbox)`, стек LwIP ещё не
поднят. Колонка не доходила даже до WiFi. Перенесли после
`happy_wifi_wait_connected()` — актуально для любого, кто включит эту
опцию, не только для того теста.

Второе — методологический урок про подбор усиления микрофона (`MIC_SHIFT`,
`audio_in.c`): тихая тестовая фраза, записанная через этот же отладчик,
показала нулевой клиппинг при усилении вчетверо сильнее текущего — но на
настоящем, более громком разговоре Whisper тут же начал галлюцинировать
случайные языки (немецкий, деванагари) вместо русской речи. Тестовая фраза
не поймала клиппинг, который проявляется на пиках погромче обычной речи.
Урок: одной спокойной тестовой записи для подбора усиления недостаточно —
нужен разговор с реальной, не отрепетированной громкостью.

**Сателлиты — сделано на сервере, клиент только веб.** Сессия больше не
привязана к одному сокету: устройства сходятся по полю `room` в `hello`,
разговор, память и ответ общие. Роль `satellite` — только микрофон, звук
уходит лишь на динамики. Микрофон выбирается по громкости один раз, на
начало реплики, и до конца не меняется: переключение посреди фразы дало бы
распознаванию склейку из двух комнат.

Замер нагрузки на плате: одно устройство 13% CPU (из 400%), два — 38%,
три — 56%, память по 2 МБ на сессию. Двойка проходит спокойно, тройка
упирается в задержку цикла событий (максимум подскочил до 10.7 мс при
ориентире 5). Замер делался на потоке тишины без разговора — живой звук
кодируется дороже, так что при двух одновременных разговорах будет выше.

Клиенты: `tools/satellite.py` для ноутбука (микрофон + WebSocket) и
страница `/satellite` для телефона. У браузера `getUserMedia` с
`echoCancellation` включает аппаратный тракт телефона — ровно то, чего нет
у нашей платы. Ни то, ни другое вживую не проверялось.

Активационное слово ищет только колонка (ESP-SR/WakeNet, на телефоне такой
модели нет) — сателлиты заменяют его кнопкой «🎤 Спросить», которая шлёт
`{"t":"ptt","state":"down"}`: ровно тот же протокол, что у физической
кнопки колонки, session.py не различает, кто прислал команду. Конец
реплики так же определяет детектор тишины на сервере, а не отпускание
кнопки. Веб-версия вдобавок требует защищённого
контекста: на Android хватает флага
`chrome://flags/#unsafely-treat-insecure-origin-as-secure`, но на iPhone
такого флага нет вовсе — там у любого браузера, включая Chrome, под
капотом системный WebKit (так требует Apple), Chromium-флаги не действуют.
Решение — второй `uvicorn.Server` на отдельном порту (`TLS_PORT`,
`main._build_tls_app`), поднятый рядом с обычным через `asyncio.gather`, а
не переключение всего сервера на HTTPS: колонка как ходила по `ws://` на
`PORT`, так и ходит, TLS не касается её вовсе. У второго `FastAPI`-объекта
намеренно нет своего `lifespan` — он делит модели и `_rooms` с первым через
модульные переменные; отдельный `lifespan` загрузил бы whisper/piper и
завёл вторую задачу ночной переиндексации фонотеки. Сертификат
самоподписанный (команда `openssl` — в `.env.example`), проверено только
что страница отдаётся и слушает `/stream` тем же обработчиком (`tests/
test_tls_app.py`); вживую проверено — подключились и с андроида (флагом
браузера), и с айфона по этому HTTPS-адресу, оба провели полный разговор
через `ptt`, включая голосовую команду `play_music`.

**Android-приложение — сделано, отдельный репозиторий.**
[`Olegkg2018/satellite-smart-speaker`](https://github.com/Olegkg2018/satellite-smart-speaker),
собрано в облаке (Google AI Studio) — на машине разработки нет ни SDK, ни
Gradle, ни JDK. Протокол проверен вживую против настоящего сервера
(`hello` с `role: satellite`, кадры `320` сэмплов/`640` байт с префиксом
`0x01`, `VOICE_COMMUNICATION` + `AcousticEchoCanceler`/`NoiseSuppressor`/
`AutomaticGainControl` для аппаратного AEC телефона).

**Страница управления — сделано.** `/` отдаёт будильники, списки, заметки
и память с возможностью удалить лишнее. Голосом это ставится одной фразой,
а посмотреть и убрать было нечем. Память показывала только сводку и число
реплик — сам разговор был виден только через `/api/memory`; страница
теперь рендерит и его (JS, без изменений на сервере — данные там уже были).

Общий вид `/` и `/satellite` вынесен в `app/webstyle.py` (токены цвета,
карточки, навигация между страницами) — обе страницы подставляют его
через `.replace()` на плейсхолдеры `__BASE_CSS__`/`__NAV__`, как уже
делалось для `__TLS_PORT__`: простая замена текста, без риска конфликта
с фигурными скобками в собственном JS каждой страницы.

**Веб-поиск переехал на DDG.** Скрейпинг `google.com/search` через
requests+BeautifulSoup стабильно возвращал ноль: Google отдаёт ботам
страницу подтверждения, а не результаты. Это же было причиной «не находит
новости».

**Киоск на /satellite (часы + погода) — сделано, живьём не проверено.**
Страница была голым пультом («Слушать»/статус) — ничего не показывала,
пока не нажать кнопку, хотя задумана лежать постоянно включённой на
подставке, как Google Nest Hub. Добавлен блок `#kiosk`: часы (чистый
клиентский JS, `toLocaleTimeString/DateString('ru-RU')`, тикают
независимо от WebSocket) и погода домашней локации из `GET /api/weather`
(`server/app/satellite_page.py`). Сетевой вызов к Open-Meteo не
задвоился: код разбора «сейчас» вынесен из `app/tools/weather.py` в
общий `_parse_current()`, которым пользуются и голосовая фраза
(`get_weather`), и новая структурная `current_conditions()` для
виджета; регрессия речи проверена тестом (`test_weather.py`). Кэш
погоды — модульная переменная с TTL 10 минут, не общая инфраструктура:
у сателлита всегда одна и та же домашняя локация. Wake Lock перенесён
с нажатия «Слушать» на саму загрузку страницы плюс переприобретение по
`visibilitychange` — раньше экран мог погаснуть до первого касания.
Статус-строка (`#state`) теперь скрыта в покое: в тишине киоск — просто
часы с погодой, без пустого «Готова».

Не входит в эту версию (по явному решению): аватар/анимация состояния,
вывод текущего трека или реплики текстом — сознательно отложены,
`#kiosk` — точка расширения под них. Не проверено вживую: реальный вид
на устройстве, поведение Wake Lock при долгом простое, поведение при
недоступности Open-Meteo на самом киоске (в тестах — да, `httpx.
MockTransport`, живого сбоя источника не ловили).
