# CLAUDE.md

Домашняя умная колонка: ESP32-S3 как тонкий клиент, вся логика на плате
S905X3 (Armbian) в Docker. Разговор ведёт облачная модель, активационное
слово ищется локально.

Подробности архитектуры, распиновки и протокола — в `README.md`.
Здесь только то, что нужно знать, прежде чем что-то менять.

## Железо и адреса

| Что | Где |
|---|---|
| Сервер | S905X3, адрес в `$HAPPY_HOST`, наружу `:8090` (внутри контейнера 8080) |
| Колонка | ESP32-S3 N16R8, адрес выдаёт роутер, подключена по USB к серверу |
| Serial колонки | `/dev/ttyACM0` **на плате**, не на машине разработки |
| Wi-Fi | задаётся в `firmware/sdkconfig` (файл в `.gitignore`) |

## Как выкатывать

Сборка образа идёт на самой плате: код туда переносится, а не собирается
локально. Адрес платы держим в переменной, чтобы он не расходился по
командам и не попадал в репозиторий:

```bash
export HAPPY_HOST=<адрес платы в домашней сети>
```

На плате код лежит по симлинку `/opt/docker/happy` — как и все остальные
контейнеры на этой машине, но физически на HDD (`/mnt/data/happy`), а не на
microSD: `data/` пишется часто (память разговоров, будильники, индекс
фонотеки каждую ночь), а у карты ограниченный ресурс перезаписи. Симлинк
прозрачен для всех команд ниже — писать можно как обычно.

```bash
# сервер
cd /home/oleg/happy
tar -czf - server/app/… | ssh "$HAPPY_HOST" 'tar -xzf - -C /opt/docker/happy'
ssh "$HAPPY_HOST" 'docker compose -f /opt/docker/happy/server/docker-compose.yml build'
ssh "$HAPPY_HOST" 'docker compose -f /opt/docker/happy/server/docker-compose.yml up -d --force-recreate'
```

Сборка занимает минуты и иногда падает по сети (таймаут pypi, IPv6 до
Docker Hub при живом IPv4) — это не ошибка кода, помогает повтор.

```bash
# прошивка: собирается на машине разработки, шьётся с платы
source /home/oleg/esp/idf_env.sh && cd firmware && idf.py build
cd build && tar -czf - happy_speaker.bin bootloader/bootloader.bin partition_table/partition-table.bin \
  | ssh "$HAPPY_HOST" 'tar -xzf - -C /home/oleg/fw'
ssh "$HAPPY_HOST" 'cd /home/oleg/fw && python3 -m esptool --chip esp32s3 --port /dev/ttyACM0 \
  --baud 460800 --before default-reset --after hard-reset write-flash \
  --flash-mode dio --flash-freq 80m --flash-size 16MB \
  0x0 bootloader/bootloader.bin 0x8000 partition_table/partition-table.bin 0x10000 happy_speaker.bin'
```

`idf.py monitor` требует настоящий терминал и в неинтерактивной сессии не
работает — логи колонки читаются скриптом на плате через pyserial с
дёрганьем RTS для сброса.

## Диагностика

```bash
curl -s localhost:8090/stats   # нагрузка, задержка цикла событий, активное слово
docker logs happy-speaker --tail 30
```

Ориентиры: `load_per_core` до ~0.7 и `event_loop_delay_ms` до 5 мс — звук
будет ровным. Во время речи сервер сам пишет в лог `звук ровный: N кадров`
либо `звук идёт рывками: …` — это честнее любых догадок про нехватку железа.
Стоимость каждой реплики тоже в логе (`app.pricing`).

## Что легко сломать

**Цикл событий.** Всё тяжёлое считается в отдельном потоке. Vosk в основном
цикле рвал WebSocket с колонкой (пинги не успевали), пересчёт частоты звука
от OpenAI давал опоздания кадров до 443 мс и рваную речь. Правило: numpy и
Vosk — только через `asyncio.to_thread`, кроме совсем мелких кусков вроде
кадра микрофона в 20 мс, где переключение потока дороже расчёта.

**Vosk не терпит общего состояния.** Модель одна на сервер (88 МБ),
распознаватель — свой у каждой сессии. Общий ломался в момент
переподключения колонки (`Failed to process waveform`), когда старая сессия
ещё жива, а новая уже пишет. Он ещё и глохнет со временем, поэтому
освежается сам после минуты тишины.

**Колонка не любит просветов в потоке.** Опустевший буфер вывода она
считала концом реплики и вставала на прогрев — отсюда «прерывистый
разговор». Сервер во время речи шлёт кадры непрерывно, прошивка ждёт
продолжения 400 мс.

**Порог громкости — адаптивный.** Фиксированный означал, что слышно только
вплотную к микрофону. Порог считается от фонового шума комнаты,
`VAD_THRESHOLD` — только нижняя граница.

**Первый кадр решает.** `play_music` ждёт реальный звук, прежде чем сказать
«Играет»: YouTube умеет отдать ссылку и не отдать поток. Локальному файлу
хватает 4 секунд, сетевому нужно 25 — `yt-dlp` раскачивается небыстро.

**Музыка не должна тормозить кадр.** Микшер ждал ffmpeg прямо внутри
тактового кадра (`readexactly` на пути звука), и раскачка ffmpeg на старте
трека давала 87 опоздавших кадров из 224, худшее опоздание 259 мс. Теперь
чтение идёт отдельной задачей с буфером на секунду; нет данных — отдаём
тишину, но кадр не задерживаем. Просвет в музыке не слышен, опоздание
кадра слышно сразу.

**Порядок реплик в памяти не гарантирован событиями.** Realtime отвечает
прямо на звук, а расшифровку вопроса Whisper досылает параллельно и часто
позже ответа. Писать по факту прихода нельзя: в памяти оказывалось «ответ,
потом вопрос», и в следующем разговоре модель читала диалог со сдвигом и
отвечала не на то, что спросили. Обмен собирается парой в `_flush_exchange`.

**Сводка памяти — поля, а не проза.** Свободным текстом туда затесалось
«необходимо запускать музыку, когда она вернётся»; модель прочла это как
поручение и на вопрос о погоде включила ABBA. Поля (`человек`,
`предпочтения`, `договорённости`, `быт`) плюс пометка «справка, не
поручение» в инструкциях.

**DNS на плате отваливается.** Цепочка `docker → systemd-resolved`
периодически подвисает: первый запрос к облаку падал с
`NameResolutionError`, отвечал только повтор — 4-7 секунд на реплику. В
`docker-compose.yml` обоих проектов прописаны свои DNS (1.1.1.1, 8.8.8.8).

**Полуоткрытое соединение держит комнату мёртвым устройством.** Колонка
теряет питание без штатного закрытия сокета (роутер/NAT промолчал, ни FIN,
ни RST) — без пинга такое соединение висит в `PeerSet` часами (стандартный
TCP keepalive в Linux — 2 часа), а переподключение того же устройства
садится вторым в ту же комнату вместо замены старого; сервер может слушать
мёртвый микрофон вместо живого. Двойная защита: `ws_ping_interval=15.0,
ws_ping_timeout=15.0` в `uvicorn.run` закрывает мёртвый сокет сам за 30
секунд, а `PeerSet.add()` (`app/peers.py`) вдобавок сразу вытесняет любого
существующего пира с тем же `device`+`role`, не дожидаясь пинга.

## Внешние сервисы

**YouTube не отдаёт аудио** с серверных адресов: скачивание получает 403,
веб-клиенты требуют PO-token. Поиск при этом работает — поэтому сбой
выглядит странно, будто трек найден, но молчит. Основной источник —
SoundCloud, YouTube оставлен запасным.

**Telegram читается без API** — через веб-превью `t.me/s/<канал>`, только
публичные каналы и только с User-Agent браузера, иначе страница приходит без
постов. Пост там не заголовок, а свободный текст с эмодзи и призывами
подписаться: всё это вычищается, иначе колонка читает вслух «подписаться
стрелка вправо».

**Realtime переотправляет весь контекст** на каждый ответ, поэтому длинный
разговор дорожает с каждой репликой. Ограничено через `truncation`
(`REALTIME_CONTEXT_TOKENS`).

**Доступ к моделям раскатывается не мгновенно.** `gpt-realtime-2.1-mini`
несколько часов отвечала `model_not_found`, хотя уже была в списке моделей.
Если модель «не существует», а ключ рабочий — это про права, а не про код.

Грабли повторились дважды на TTS: `gpt-4o-mini-tts` числится в
`/v1/models`, но на запрос отвечает 403 «does not have access»; `tts-1-hd`
в списке нет вовсе. Рабочая — `tts-1`. Прежде чем менять модель, проверяй
не список, а живой вызов: список врёт.

## Соседний проект на той же плате

Рядом крутится `xiaozhi-esp32-server` — чужой сервер под ту же ESP32,
поднятый для сравнения. Это отдельный контейнер и отдельная прошивка,
с нашим `happy` он не связан ничем, кроме железа.

| | happy | xiaozhi |
|---|---|---|
| Исходники | этот репозиторий | `/mnt/data/xiaozhi-esp32-server` |
| Данные | `/opt/docker/happy/server/data` | `/mnt/data/xiaozhi-server` |
| Порты | 8090 | 8005 (ws), 8006 (OTA) |
| Схема | речь-в-речь (Realtime) | `ASR → LLM → TTS` |

Прошивка у платы может быть только одна: чтобы попробовать xiaozhi, её
перешивают их бинарником, обратно — нашим (`/home/oleg/fw`, смещения в
`flasher_args.json`).

Что оттуда пригодилось нам: приём с кольцевым буфером перед активационным
словом, отладчик звука по UDP, инициализация панели ST7789. Что не
пригодилось: их вывод на экран (55 КБ C++ поверх LVGL, завязан на их
`board.h`) и конвейерная схема разговора — речь-в-речь мы выбрали
сознательно.

Замер локального синтеза на этой плате (Cortex-A55, 4 ядра, без GPU):
Piper RTF 0.57, Silero v3 RTF ~0.9 после прогрева. Прогрев Silero стоит
40 секунд и делается при старте сервера, иначе первая фраза после
перезапуска ждёт всё это время. Задача почти не параллелится: учетверение
потоков даёт 9% прироста, всё упирается в одно ядро.

## Настройки, которые меняют поведение сильнее всего

Всё в `server/.env` (образец — `.env.example`), пересборка не нужна,
достаточно `up -d --force-recreate`.

- `VOICE_PROVIDER` — `openai_realtime` (спич-ту-спич) или `claude`
  (Whisper → Claude → Piper, работает без интернета к OpenAI).
- `OPENAI_REALTIME_MODEL` — `gpt-realtime`. Есть и `-2.1-mini` втрое
  дешевле, но на неоднозначной речи она чаще путает инструменты.
- `STT_PROVIDER` / `TTS_PROVIDER` — `local` или `openai`; облачные заметно
  быстрее локальных на этом железе.
- `WAKE_WORD` — слово подлиннее надёжнее: короткие притягивают созвучия
  («Алиса» ловится на «Ларису»).

## Планы развития

Не готовые решения, а то, что обсуждали и стоит учитывать при следующем
подходе к теме.

**Экран 2.0" ST7789V — сделано, но живьём не проверено.** Отрисовка
переехала на плату: сервер шлёт `{"t":"text","value":"…"}`, а рисует
`display_st7789.c`. Кадр собирается полосами по 32 пикселя в PSRAM —
целиком RGB565 240x320 (150 КБ) во внутреннюю память не влезает. Шрифт с
кириллицей запечён в прошивку (`tools/make_font.py`, 168 глифов, 8 КБ).
Инициализация панели — штатный `esp_lcd`, взята из `bread-compact-wifi-lcd`
у 78/xiaozhi-esp32; их собственный вывод на C++ поверх LVGL не переносится.

Экран физически не подключён — код собирается и тесты шрифта проходят на
хосте, но на живой панели ничего не проверялось. Распиновка под гребёнку
платы XH-S3E-AI: `MOSI=41`, `CLK=42`, `CS=44 (RXD)`, `DC=43 (TXD,
перемычка)`, `RST` на 3V3 (сброс командой), подсветка внутри модуля. Пять
контактов из семи садятся в разъём как есть; `DC` и `RST` отгибаются —
`RST` обязательно, иначе он попадёт на `UIN` с пятью вольтами. UART при
этом свободен: консоль идёт по USB (`ttyACM`).

**Мимика на большом экране — не начато.** Когда экран заработает, его
надо чем-то заполнить. У 78/xiaozhi-esp32 это LVGL с коллекцией PNG на
21 эмоцию — тянуть LVGL ради этого не хочется. Дешевле: наш же
`make_font.py` умеет печь любой размер, значит можно сгенерировать второй
шрифт кегля 96 из десятка символов-лиц. Ограничение: в DejaVuSans
пиктограмм немного и цветных эмодзи нет вовсе — будут одноцветные
силуэты, зато килобайты флеша и ноль зависимостей. Альтернатива — взять
готовые Twemoji 64×64 из
[78/xiaozhi-assets-generator](https://github.com/78/xiaozhi-assets-generator)
и перегнать в RGB565.

**Распознавание голоса (кто говорит) — реально достижимо.** Раньше сказал,
что это едва ли возможно на этом железе — неверно. В `xinnan-tech/
xiaozhi-esp32-server` (сервер, который пользователь тестировал под тем же
модулем ESP32, см. `voiceprint_provider.py`) это обычный HTTP-вызов к
внешнему API `/voiceprint/identify` с порогом схожести — тот же принцип,
что у нас уже работает с погодой и распознаванием речи: облако считает,
плата и сервер только передают. Стоит вернуться к этой идее.

**Суммирование памяти — сделано.** Вытесненное из окна сворачивается
`memory_summary.fold_in` через `gpt-4o-mini` (отдельная дешёвая модель, не
та, что ведёт разговор). Сводка структурная: поля `человек`,
`предпочтения`, `договорённости`, `быт`. Прозой уже обожглись — см.
«Сводка памяти — поля, а не проза» выше.

Их подход отличается моментом: `mem_local_short` в xiaozhi сворачивает всё
одним разом при закрытии сессии, мы — на каждом вытеснении. Наш дороже по
вызовам, зато переживает внезапный обрыв; у них при падении контейнера
сессия теряется несвёрнутой.

**Выбор модели — не копировать.** Там же дежурил `deepseek-chat` —
вероятная причина, по которой колонка на этом проекте была «тупой»: слабее
Claude Opus 5 и `gpt-realtime-2.1-mini` в надёжности вызова инструментов и
общей адекватности ответов. Память и логирование там были в порядке —
дело было в модели, не в архитектуре.

**Учёт расходов в Telegram.** Кабинет OpenAI для «остатка на счету» не
подходит — данные там с задержкой и нужны отдельные права, поэтому
стоимость уже считается на месте по токенам ответа (`app/pricing.py`).
Сейчас это работает только за одну сессию и никуда не сохраняется. Чтобы
слать в Telegram «сколько потрачено» — по запросу голосом или раз в сутки
сводкой, — нужно копить этот же посчитанный итог на диск (day-to-day,
как `data/alarms` или `data/lists`), а не искать API «остатка», которого
для такого ключа попросту нет.

**Другие голосовые модели, кроме `gpt-realtime-2.1-mini`.** Стоит
свериться с актуальной документацией, а не полагаться на память — цены и
состав предложений меняются. Архитектура уже рассчитана на смену бэкенда
(`VOICE_PROVIDER=openai_realtime` или `claude`, см. `app/voice.py`), так
что третий вариант (например, Gemini Live API) — это ещё один класс рядом
с `RealtimeVoice`, а не переписывание с нуля.

**Telegram-бот в обе стороны.** Сейчас бот только пишет наружу — дублирует
разговор (`app/notify.py`) и читает публичные каналы для новостей
(`app/tools/telegram.py`); входящие сообщения сервер не читает вовсе.
Чтобы бот принимал задания колонке, составлял и выводил списки, брал текст
или файл на осмысление («прочти и расскажи, что думаешь») — нужен
long-polling или webhook и разбор команд. Это открывает текстовый канал
управления умным домом снаружи разговора на кухне (дом на 192.168.2.14
управляется через HA), и доверие к этому каналу стоит обдумывать отдельно
от голоса рядом с колонкой, а не переносить как есть.

**Тест на `agent.py` (ручной цикл tool-use у Claude) не написан.** Ревью
августа 2026 просило хотя бы один тест на связку «tool_use → tool_result →
повторный запрос» с моком Anthropic-клиента. `session.py` тестами уже
покрыт (`tests/test_session.py`), а `agent.py` — нет: код не используется
в рантайме при `VOICE_PROVIDER=openai_realtime` (сейчас так и стоит), но
именно поэтому он опаснее всего в день, когда его снова включат. Отложено
по объёму работы (мокать стриминг Anthropic сложнее, чем bare-instance
тесты на Session), не забыто.

**Opus вместо сырого PCM — сделано.** Канал сжат примерно в 15 раз.
`firmware/main/audio_opus.c` — обёртка над `espressif/esp_audio_codec`,
`hello`/`ready` согласуют кодек, откат на PCM при отсутствии Opus с любой
стороны штатный. Первая версия звала кодек синхронно из `afe_fetch` и
`websocket_task` и валила их тайминги: стека 4096 не хватало под кодек
(Guru Meditation на активационном слове), а конкуренция за приоритет 5
рвала WebSocket ровно в момент начала записи. Теперь это отдельная задача
с очередями.

**Буфер перед активационным словом — сделано.** `firmware/main/wake_cache.c`:
кольцо на секунду в PSRAM, при активации накопленное уходит первым, до
живого потока. По кнопке кольцо сбрасывается — там начало реплики известно
точно. Раньше слитное «компьютер, включи музыку» приходило как «ключи
музыку».

**Отладчик звука — сделано.** `firmware/main/audio_debug.c` дублирует то,
что слышит микрофон, по UDP; `firmware/tools/listen.py` принимает и пишет
в wav. По умолчанию выключен. Появился после того, как качество
распознавания дважды пришлось оценивать по косвенным признакам —
расшифровкам на румынском и доле опоздавших кадров.

**Сателлиты — сделано на сервере, клиент только веб.** Сессия больше не
привязана к одному сокету: устройства сходятся по полю `room` в `hello`,
разговор, память и ответ общие. Роль `satellite` — только микрофон, звук
уходит лишь на динамики. Микрофон выбирается по громкости один раз, на
начало реплики, и до конца не меняется: переключение посреди фразы дало бы
распознаванию склейку из двух комнат.

Замер нагрузки на плате: одно устройство 13% CPU (из 400%), два — 38%,
три — 56%, память по 2 МБ на сессию. Двойка проходит спокойно, тройка
упирается в задержку цикла событий (максимум подскочил до 10.7 мс при
ориентире 5). Замер делался на потоке тишины без разговора — живой звук
кодируется дороже, так что при двух одновременных разговорах будет выше.

Клиенты: `tools/satellite.py` для ноутбука (микрофон + WebSocket) и
страница `/satellite` для телефона. У браузера `getUserMedia` с
`echoCancellation` включает аппаратный тракт телефона — ровно то, чего нет
у нашей платы. Ни то, ни другое вживую не проверялось.

Активационное слово ищет только колонка (ESP-SR/WakeNet, на телефоне такой
модели нет) — сателлиты заменяют его кнопкой «🎤 Спросить», которая шлёт
`{"t":"ptt","state":"down"}`: ровно тот же протокол, что у физической
кнопки колонки, session.py не различает, кто прислал команду. Конец
реплики так же определяет детектор тишины на сервере, а не отпускание
кнопки. Веб-версия вдобавок требует защищённого
контекста: на Android хватает флага
`chrome://flags/#unsafely-treat-insecure-origin-as-secure`, но на iPhone
такого флага нет вовсе — там у любого браузера, включая Chrome, под
капотом системный WebKit (так требует Apple), Chromium-флаги не действуют.
Решение — второй `uvicorn.Server` на отдельном порту (`TLS_PORT`,
`main._build_tls_app`), поднятый рядом с обычным через `asyncio.gather`, а
не переключение всего сервера на HTTPS: колонка как ходила по `ws://` на
`PORT`, так и ходит, TLS не касается её вовсе. У второго `FastAPI`-объекта
намеренно нет своего `lifespan` — он делит модели и `_rooms` с первым через
модульные переменные; отдельный `lifespan` загрузил бы whisper/piper и
завёл вторую задачу ночной переиндексации фонотеки. Сертификат
самоподписанный (команда `openssl` — в `.env.example`), проверено только
что страница отдаётся и слушает `/stream` тем же обработчиком (`tests/
test_tls_app.py`); вживую проверено — подключились и с андроида (флагом
браузера), и с айфона по этому HTTPS-адресу, оба провели полный разговор
через `ptt`, включая голосовую команду `play_music`.

**Android-приложение — сделано, отдельный репозиторий.**
[`Olegkg2018/satellite-smart-speaker`](https://github.com/Olegkg2018/satellite-smart-speaker),
собрано в облаке (Google AI Studio) — на машине разработки нет ни SDK, ни
Gradle, ни JDK. Протокол проверен вживую против настоящего сервера
(`hello` с `role: satellite`, кадры `320` сэмплов/`640` байт с префиксом
`0x01`, `VOICE_COMMUNICATION` + `AcousticEchoCanceler`/`NoiseSuppressor`/
`AutomaticGainControl` для аппаратного AEC телефона).

**Страница управления — сделано.** `/` отдаёт будильники, списки, заметки
и память с возможностью удалить лишнее. Голосом это ставится одной фразой,
а посмотреть и убрать было нечем. Память показывала только сводку и число
реплик — сам разговор был виден только через `/api/memory`; страница
теперь рендерит и его (JS, без изменений на сервере — данные там уже были).

Общий вид `/` и `/satellite` вынесен в `app/webstyle.py` (токены цвета,
карточки, навигация между страницами) — обе страницы подставляют его
через `.replace()` на плейсхолдеры `__BASE_CSS__`/`__NAV__`, как уже
делалось для `__TLS_PORT__`: простая замена текста, без риска конфликта
с фигурными скобками в собственном JS каждой страницы.

**Веб-поиск переехал на DDG.** Скрейпинг `google.com/search` через
requests+BeautifulSoup стабильно возвращал ноль: Google отдаёт ботам
страницу подтверждения, а не результаты. Это же было причиной «не находит
новости».
